1日常运维操作手册

创建新旅程、Token、FC 代理、CU 计费、发布推送 —— 今后所有操作的步骤与逻辑，以及哪些动作会花钱（CU）。

1.1 创建新旅程（新行程页面）

运行「创建新旅程.ps1」→ 复制 index.html 为模板，起中文名（如 川西环线5日游.html）→ 自动推导 dataPath = data/文件名/trip.json→ 首次加载：有 Token 时自动检测旧目录并一键迁移
  • 命名规则（方案A）：中文名直接用，无需转英文。新页面 dataPath 由文件名自动推导，无需改任何代码。
  • 默认首页特判：index.html / default / 空 → data/格聂南线/trip.json。
  • 数据隔离：每个行程独立 data/行程名/trip.json，互不干扰。
  • 迁移逻辑：重命名页面后首次打开，新路径不存在 → 自动扫描云端 data/ 目录 → 弹窗确认 → 一键复制旧数据到新路径并刷新（仅限有 Token 的编辑者，游客只读不弹窗）。
  • 新旅程即最优版本：创建脚本以 index.html 为模板，所以 index.html 的每次优化会自动成为新旅程的初始状态。
⚠️
本地 file:// 打开时：每个 HTML 文件的 localStorage 相互独立——index 里填的 FC 地址 / Token，MiletoPuzhehei 里看不到，需各填一次；线上 GitHub Pages 同源共享，配一次即可。

1.2 Token 管理

项目说明
存储位置localStorage.gh_token（仅存浏览器本地，不落盘、不上传）
作用有 Token → 走 GitHub API 读写（国内可达）；无 Token → jsDelivr CDN 只读，失败降级本地缓存
获取方式GitHub → Settings → Developer settings → Personal access tokens → 勾选 repo 权限
在哪里填页面 → 同步设置 → Token 管理
丢失场景清浏览器缓存/换浏览器/换电脑 → Token 丢失需重新填写
安全红线Token 是敏感信息：不写入任何上传文件、不在对话/文档中明文展示；本机「配置信息.txt」已存明文，务必妥善保管
💡
加载链路（理解“卡连接中”）：有 Token → GitHub API（5s 超时）→ 失败走 CDN(4s) → raw(4s) → 降级本地缓存。无 Token → CDN → raw → 降级。改完云端后若页面还是旧内容，先 Ctrl+F5 强刷，别急着报 bug。
⚠️
重要澄清：「配置信息.txt」≠ 程序配置。那个 txt 是你手动记的备忘（含 Token 明文，注意别外传），程序运行时不读它。程序真正读的是浏览器记忆本（localStorage）。所以你在 txt 里改什么都没用——要在页面的「同步设置」弹窗里填才算数。

1.4 CU 计费逻辑：哪些动作花钱

CU = 阿里云函数计算的计费单位，通俗说就是「中转站跑腿的账单」。当前架构下 FC 只承担「写入/读取/上传/AI 转发」，轮询和游客读取都走 CDN，所以调用量本来就很低。

动作是否消耗 FC(CU)说明
编辑保存（cloudSave）消耗POST 1 次；首次跨域还有 1 次 OPTIONS 预检（已被 24h 缓存头砍掉，一天内仅首次）
上传图片（uploadTripImage）消耗走 FC action=upload；未部署 v6+ 时回退直连 GitHub API
读取云端（loadViaFcProxy）消耗配置了 FC 地址的编辑者加载时 POST action=read
AI 大模型调用（callLLM）消耗（若启用）走 FC action=ai 转发；未配置 AI 则完全不产生
60s 自动轮询（cloudPollCheck）不消耗走 GitHub API / CDN / raw，不经过 FC —— 挂机看行程不会产生 FC 费用
游客访问 / 无 Token 加载不消耗jsDelivr CDN 读取，与 FC 无关
有 Token + FC 开关关闭不消耗直接连 GitHub API（绕过中转站）——功能正常，但国内直连慢、可能不稳定；完全不产生 CU
高德地图 / 天气接口不消耗直接调用高德/Open-Meteo，走各自免费额度

💡
结论：关 FC = 省钱但不快；开 FC = 花钱一点点但体验好。每月 100 万次免费，正常一年 3 次旅行基本 ≈ 0 元，所以平时就开着 FC 用，别关。

计费规则（2026-08-06 已实测确认）

  • 每月前 100 万次调用免费（三年试用后按量，年成本约 0.3~0.5 元）——按您每年 3 次旅行的用量绰绰有余。

1.5 修改代码后的完整发布流程

本地改 index.html / MiletoPuzhehei.html / fc_proxy.py→ 改 FC 代码需去阿里云控制台重新部署→ 推 HTML 到 GitHub 仓库（git push）→ GitHub Pages 自动更新→ 浏览器 Ctrl+F5 强刷验证
⚠️
最容易“看似没生效”的场景：只改了本地没推送（线上是旧版）；或推送了但浏览器缓存（需强刷）。排查顺序：本地文件 → 云端文件（GitHub 网页看大小）→ 强刷。

1.6 常见疑问 FAQ（你问过的问题，一次讲透）

Q1：本地配好了 Token / FC 地址，把文件传到 GitHub 后，要不要重新配置？

💡
要！全部重新配一遍。这是本项目最容易误会的一点：
Token、FC 地址、FC 开关、AI 配置，都不存在文件里，而是存在「你当前打开的浏览器」的记忆本（localStorage）里。
你把 HTML 文件传到 GitHub，上传的只是「程序本体」，记忆本不会跟着文件走。换个网址打开 = 换了一本全新的空白记忆本，得重新填。

打比方：HTML 文件是「软件」，Token/FC 地址是「登录密码」。你换了个网址打开，就像换了台新手机——软件装上了，但微信得重新登录。

打开方式记忆本有几本？要怎么配？
本地双击打开（file://）每 1 个 HTML 文件 1 本（index 配的 Mileto 看不到）每个页面各填一次
云端网址打开（GitHub Pages）整个网址共用 1 本填一次，全站所有行程共享 ✅
⚠️
实际建议：以云端网址为「主战场」——在网址端配好 Token + FC 地址，一次配好全站生效；本地文件主要用于改代码/测试，本地偶尔用就再填一次（或只在云端编辑数据）。

Q2：本地把 FC 代理开关关掉了，网址端要不要也关？

✅
不用！本地那本记忆本改了，云端那本毫无影响，两份记忆互不相干。
想让云端网址也走直连，才需要到网址端单独关一次。同理：本地开了，云端不会自动开。

Q3：关掉 FC 开关后，数据还能保存吗？

✅
能。关 FC = 不走中转站 = 浏览器直接连 GitHub 存数据。功能完全正常，只是国内直连慢、可能卡，尤其是保存含图片的大文件时。不花 FC 的钱，代价是体验。

Q4：我又不编辑，为什么"管理员 + FC 关"不能等于游客？（身份由 Token 决定，不是由编辑模式决定）

状态加载/检查走哪条路看到的数据能保存吗
游客（没 Token）国内仓库分店（CDN）缓存版，可能不是最新（CDN 刷新要几分钟~几小时）✗
管理员 + FC 开中转站 → GitHub 实时通道最新✓
管理员 + FC 关直连 GitHub 实时通道最新✓
💡
为什么管理员不能走 CDN 当游客？因为 CDN 是缓存（旧数据），管理员必须看到最新数据（刚编辑完要立刻看到、还要检测别人是否改了），所以只要记忆本里有 Token，加载和 60s 自动检查就走"实时通道"（GitHub API），FC 开关只影响这条通道快不快，不影响走哪条通道。
想当纯游客：用无痕窗口 / 手机浏览器打开（那里没你的 Token），或临时清除 Token；平时日常浏览用游客通道完全免费且快。

Q5：网址端 FC 开关一直开着，会不会一直产生 CU？

✅
不会！开开关 ≠ 在计费。CU 是"按次收跑腿费"，不是"按月收房租"——开着但没人找它跑腿 = 一分钱不花。
花钱的只有：打开页面加载（1 次）、每点一次保存（1 次）、传一张图（1 次）。60 秒自动检查（轮询）被特意设计成不走 FC，挂机一整天 CU 一分不涨。
⚠️
唯一会"一直产生"的是阿里云控制台的「最小实例数 = 1」（函数常驻，没人用也每小时计费 ≈ 7 元/月），去控制台确认是 0。
终极省钱法：不旅行时去控制台「停用函数」= 绝对 0 元；下次旅行前启用（1 分钟），页面配置不用动。

1.7 🆕 编辑模式自动切换管理员/游客（2026-08-06 新增）

从此不用再手动管理 Token——平时打开页面就是游客（走 CDN 快、零成本），点「编辑」输密码后自动变管理员，点「完成编辑」自动回到游客。核心是 Token 的「双区存储」：

存储区通俗叫法存什么什么时候消失
临时记忆（sessionStorage）活跃 Token当前编辑会话的 Token退出编辑 / 关标签页 / 关浏览器 → 自动清
长期记忆（localStorage）记住版 Token勾选「记住本设备」时保存只在「同步设置」点删除才消失
日常打开 = 游客（CDN 快、零成本）→ 点「编辑」输密码→ 自动激活 Token（记住版自动搬，无记住版则弹窗输入一次）→ 编辑完点「完成编辑」→ 自动删 Token + 停轮询 = 回游客
  • 第一次怎么配：点「编辑」→ 输管理员密码 → 弹窗粘贴 Token → 选「记住本设备」→ 以后每次进编辑全自动，无需再输。
  • 不想记住：弹窗选「取消」（不记住）→ Token 仅本次编辑有效，退出或关标签页自动清除，最严格最安全。
  • 中途刷新 F5：临时记忆还在 → 编辑不打断，不用重输。
  • 老用户无缝兼容：以前存过的 Token 自动变成"记住版"，首次进编辑自动搬，无感。
  • 兼容旧逻辑：同步设置里「保存 Token」= 记住本设备；「测试 Token」不污染记忆；「删除 Token」两者全清。
✅
已通过 15 项行为模拟测试 + 双文件语法/一致性校验（游客判定 / 记住版自动搬 / 退出清除 / 临时模式 / 测试恢复 / 全删）。改动仅本地两个 HTML，需推送云端 GitHub Pages 才在线生效。

  3. 验证：编辑任一 POI → 「自动填入」→ 若 desc/detail 由 AI 生成即成功；或打开旅途提示弹窗看叙述风格。

针对本项目的结论与建议

💡
推荐：GLM 为主（首选 glm-4.7-flash）。理由：① 本项目 AI 最核心的用途是「智能匹配简介」——需要模型稳定输出 JSON（desc/detail），GLM 的结构化输出和 JSON 解析兼容性最好；② 长期免费、无额度焦虑；③ 注册最快（bigmodel.cn 一个页面搞定）；④ 200K 上下文对「生成达人叙述式旅途提示」也绰绰有余。
💡
Hunyuan-Lite 作为备选：256K 上下文在免费档里最激进，适合超长文本；若 GLM 偶尔抽风，可在配置里直接换 provider=自定义 + 混元地址，无需改代码。两款都免费，双 Key 配置 = 双保险。

基于两天开发中真实发生的重复劳动、错误指令和消耗复盘 —— 哪些习惯在浪费你的积分/token，以及今后怎么跟 AI 高效协作。

3.1 这两天真实踩过的坑（按浪费程度排序）

🥇 天气模块反复返工 —— 改数据源改了 4 轮
Open-Meteo →（误判“海外不可达”）→ 高德 4 天 →（天数不够）→ 双源合并 →（用户实测 Open-Meteo 其实可达）→ 恢复 Open-Meteo 主源。本质错误：没先验证数据源就改代码。若一开始用真实请求（WebFetch）确认 Open-Meteo 可达，能省下大半天。
🥈 双文件同步反复出漏 —— 同一批功能同步 3 次仍有差异
index.html 和 MiletoPuzhehei.html 必须保持一致（150+ 函数），正则批量同步多次出错：漏函数本体（checkAndMigrate 导致“卡连接中”）、漏 HTML 元素（editImgFile 导致 null 报错）、CSS 不一致（卡片 padding 白边）、替换把函数名改坏（renderMap 递归）。本质错误：改完只验证了“语法”，没验证“两端一致”。
🥉 FC 函数 event 格式连猜 3 轮（dict → HTTP 报文 → JSON bytes）
因为没先部署“回显诊断版”看真实 event，靠猜浪费 3 轮部署-验证循环。教训：云函数排障先回显，不猜格式。
🎗️ 封面“白边/不饱满”反复修 —— 从图片源猜错到容器 padding
以为是外链图加载问题，实际根因是 .overview-day-card 的 padding:14px vs 0。教训：视觉 bug 要对比完整 CSS 链，别只看局部。
🎗️ 天气排序逻辑改了 5+ 次（firstOrder → needWeather → shouldShowWeather → 10km 去重）
每次“加一点”规则，业务规则越叠越复杂。教训：需求一次说清“判定规则完整版”，别挤牙膏。
🎗️ 域名拼写错误 swr4mygeqi / swyrmygeqi 排查半天
凭记忆写域名。地址类信息必须复制粘贴。

3.2 积分 / Token 消耗大户（你感觉“小改动却很贵”的原因）

#浪费场景为什么贵对策
1 挤牙膏式提需求
（“再加一点”“再改一下”）		 每次修改都是一整轮完整调用：重读 6-7 千行 HTML + 改代码 + 验证 + 汇报。旅途提示功能分了 6+ 轮才定型 一次把需求说全：最终文案、样式、交互一次给齐；攒 3~5 个小改动合并成一批做
2 只改一个文件，下次还要再改另一个 双文件架构下默认只改 index，Mileto 遗漏 → 发现后再改一遍 → 双倍消耗 每次提需求就明确说「全部修改」或「只改某个文件」（项目长期规则）
3 反馈 bug 不带截图/不带细节 AI 靠猜，猜错一轮再猜一轮。封面白边问题就猜了 2-3 轮 截图 + 操作步骤 + 期望行为 + 实际行为，四要素齐了再提问
4 探索性指令
（“试试看”“先这么搞”）		 探索指令和最终指令成本相同（都要完整执行），试错了再执行一遍=翻倍 先让 AI 出方案/影响面，确认后再执行；探索用小规模验证（如先改一行测效果）
5 改完不推送/不验证就提下一个需求 本地改了没推 GitHub → 你测的是旧版 → 报“没生效” → 排查半天发现是缓存/未部署 每轮改完：AI 说明改动点 → 推送 → 你强刷验证 → 再开新需求
6 让 AI 凭记忆/猜测回答数据源、域名、API 行为 猜错→验证→返工（Open-Meteo 可达性、FC event 格式、FC 域名都栽过） 涉及外部依赖：要求 AI“先实测再下结论”；涉及地址：复制粘贴
7 没有版本回退点 git 只有一个初始 commit，所有改动未提交。一旦改坏（曾发生脚本把文件写坏到 552KB），修复要重新解释一遍上下文，代价极大 每完成一个里程碑 commit 一次（哪怕就一句“天气模块完成”），改坏能一条命令回退
8 微调文案类需求反复迭代 “这句话再改柔和点”“再口语一点”——每轮都全量重跑 文案类需求给出最终期望的范例句子，一次定型
9 用模糊词描述 bug “填充不饱满”“有点怪”“不对”——AI 无法定位，只能盲猜 描述精确到：哪个页面、哪个按钮、哪个元素、具体现象（如“卡片四边有 14px 白边”）
10 反复让 AI 重读/重述旧上下文 新开对话后 AI 不认识项目，又要从零读文件了解架构 项目记忆已存在 .workbuddy/memory/，开新对话时先让它读「项目长期记忆」再干活

3.3 高效对话的黄金法则（今后照着做）

一次说全
目标 + 涉及文件 + 范围 + 验收标准
先方案后执行
大改动先要影响范围再动手
先验证再改码
数据源/接口/域名一律实测
改完即验证
推送 + 强刷 + 确认，再开下一项
  1. 需求四要素模板：① 要做什么 ② 改哪些文件（全部 / 只改 index / 只改 Mileto）③ 做成什么样（可附截图或最终文案）④ 做完怎么验收。
  2. 提 bug 四要素：截图（或复现路径）+ 操作步骤 + 期望行为 + 实际行为。先自行强刷 Ctrl+F5 排除缓存。
  3. 大改动先要方案：说“先别改，给我方案和影响范围” —— 一次确认可以省掉整轮返工。
  4. 改代码前先让 AI 验证假设：涉及天气源/API/云函数/域名，要求“先实测再下结论”，不许猜。
  5. 小改动合并批处理：攒 3-5 个点一次说清，比 5 次小对话省一半以上消耗。
  6. 里程碑即提交：每完成一个功能块，让 AI git commit 一次，建立回退点。
  7. 新对话先加载记忆：项目记忆在 .workbuddy/memory/，开局让 AI 先读「MEMORY.md + 最近日志」再干活。
  8. 敏感信息管理：Token、API Key 只在本地配置/安全文件里，明确要求 AI 不得写入上传文件、不在回复中明文回显。
  9. 验收时双端验证：双文件改动必须让 AI 报告“两文件语法通过 + 关键点 grep 计数”，而不是只说“改完了”。
✅
本项目专属规则（已在记忆中长期保存）：
① 用户提修改意见时，AI 先问「全部修改」还是「只改某个文件」；
② 双文件同步后必须验证「函数定义+调用成对」；
③ 云端探测一律走 GitHub API（raw/CDN 国内不可达）；
④ 云函数排障先部署回显诊断版，不猜 event 格式。
