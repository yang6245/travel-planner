## 二、问题清单（按严重级别）

### 🔴 P0-1 无仓库白名单校验 —— 代理可被滥用（必须修复）

- **位置**：`handler()` 第 72-75 行，`owner/repo/path` 直接取请求 payload，未校验
- **风险**：
  1. 任何人拿到你的 FC 公网地址，携带**自己的** GitHub Token，即可通过你的函数写入**任意 GitHub 仓库**（消耗你的 FC 免费额度）；
  2. 你本人的 Token 若被泄露，攻击者可借助你的代理写入你的任意仓库（不只是 travel-planner）；
  3. 函数沦为开放转发代理，可被用于刷接口、绕过限制。
- **修复**：白名单校验 —— 只允许 `yang6245/travel-planner`，且 `path` 必须以 `data/` 开头，否则 403。

### 🟠 P1-1 空请求/GET 直接访问触发 500 崩溃（已修复）

- **位置**：原代码对 FC Web 函数 GET 请求（`event=''`）执行 `json.loads('')` 抛异常 → 500
- **实测**：curl GET 返回 `{"error": "FC 内部错误: Expecting value: line 1 column 1 (char 0)"}`
- **修复**：v2 将 event 解析抽为 `_parse_event()`，空 body 返回友好 401，不再崩溃。

### 🟠 P1-2 请求体无大小限制（建议修复）

- **位置**：`handler()` 未检查 body 长度
- **风险**：恶意发送超大 body → 实例内存占满、费用被消耗（图片 base64 场景尤其应设上限）
- **修复**：> 10MB 直接返回 413。

### 🟠 P1-3 GitHub 网络抖动无重试（建议修复）

- **位置**：`handle_save()` / `handle_read()` 单次 `urlopen`
- **风险**：GitHub 偶发 5xx / 429 / 连接超时，保存直接失败，用户只能手动重试
- **修复**：对 5xx/429/网络异常做指数退避重试 2 次；4xx 不重试。

### 🟠 P1-4 关键配置硬编码（建议修复）

- **位置**：owner/repo/path 默认值散落在 handler 中
- **风险**：换仓库/换分支需改代码重新部署
- **修复**：集中为常量 + 支持 FC 环境变量覆盖（`GH_OWNER` / `GH_REPO` / `MAX_BODY_BYTES`）。

### 🟡 P2-1 CORS `*` 全开放（可接受，留意）

- 任意网站可跨域调用，但无 token 会被拒，实际风险低
- **建议**：如后续绑定固定域名（GitHub Pages），可收窄 `Access-Control-Allow-Origin` 为具体域名。

### 🟡 P2-2 响应未设缓存控制（顺手修复）

- **修复**：v2 增加 `Cache-Control: no-store`（防敏感数据落缓存）+ `X-Content-Type-Options: nosniff`。

### 🟡 P2-3 Token 可能出现在 FC 日志（提醒）

- 阿里云 FC 可能记录请求头（含 `X-GitHub-Token`）
- **建议**：控制台关闭请求头日志记录；GitHub Token 只授予 **repo 最小权限**（fine-grained，仅本仓库）。

## 三、v2 改动点汇总

| 位置 | 改动 | 收益 |
|---|---|---|
| `handler()` | 新增仓库白名单校验 | 杜绝代理被滥用（P0） |
| `_parse_event()` | 解析逻辑抽函数 + 空 body 容错 | 代码可读性 + GET 不再 500（P1-1） |
| `handler()` | body 长度检查 >10MB 返回 413 | 防资源滥用（P1-2） |
| `_urlopen_with_retry()` | 新增 5xx/429/网络异常重试 | 保存更可靠（P1-3） |
| 模块级常量 | `ALLOWED_OWNER/REPO/MAX_BODY_BYTES` + 环境变量覆盖 | 配置集中、可运维（P1-4） |
| `json_response()` | 新增缓存/嗅探安全头 | 响应安全（P2-2） |
| `handle_save()` | 增加 `content` 空值校验 | 避免无效请求打到 GitHub |
| `handle_read()` | 统一走重试封装 | 一致性与可靠性 |
